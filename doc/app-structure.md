# App Target Structure

How the `Yellowhammer` app target is organised, and the rules that keep it that way. This file covers
the app target only; `Packages/YellowhammerKit` has its own module rules in CLAUDE.md (MB1–MB5).

---

## 1. One target, folders, no UI modules

The app is a single target organised by folders. The UI is not split into Swift modules — not a
`YellowhammerView`, and not one module per feature.

- A module exists in this repo to enforce a binding rule (ADR-001/002/003, "shell, not host"). A UI
  split enforces none, and costs `public` on every view, `Bundle.module` for assets and the theme, and
  a hand-linked package product per module.
- Logic belongs in `Packages/YellowhammerKit`, in the module named after the glossary term it holds —
  the Pulse's view state and the Journal read that fills it live in `Pulse`, not in the app. What stays
  in the app is views, and glue that cannot run outside a `.app` bundle (notifications, Sparkle,
  launching `yh`).

Revisit only if app-target build times become a real cost, the design system gains a second consumer,
or a boundary appears that folders cannot hold.

---

## 2. Layout

```
Yellowhammer/
  App/              YellowhammerApp, AppLaunch, Updater, menu commands
  Configuration/    ConfigurationDirectory, ConfiguredProjects, SetupEngine
  DesignSystem/
    Theme/          generated by ThemeKit from theme.json — never edit by hand, never move
    Brand/          e.g. the logo view
    Effects/
    Components/     generic reusable views: Surface, NavigationRow, …
  DevSupport/
    Previews/       Debug-only fixtures, Playground and Gallery
  Extensions/
    SwiftUI/
    Foundation/
  Integration/      system and third-party integrations
    Headless/       HeadlessPost, HeadlessPermissionRequest, NotificationPermission
  Features/
    Overview/       the main window: Sidebar, Pulse, Inspector, Toolbar
    Settings/       the Settings window (Cmd+,)
    AddProject/     the Setup wizard sheet
    Shared/         domain-aware views reused across features
```

`Overview` is the code name for the spec's main window (Sidebar + Pulse + Inspector). Its root view is
`OverviewWindow`; the Settings window's is `SettingsWindow`. "Overview" is a code name only — it never
appears in UI copy, and it is always one selected Project's overview, never a blend of several (R20).
The feature is not called "Landing": in the spec, Landing is the `land` Act and the `landing` epic.

---

## 3. Rules

- **Organise by feature, not by type.** No top-level `Views/`, `Models/` or `ViewModels/`.
- **Dependencies point one way:** `Features/*` → `Features/Shared` → `DesignSystem`. A feature never
  reaches into a sibling feature; anything two features need moves down to `Shared`.
- **`DesignSystem` knows nothing about Yellowhammer.** It holds no glossary term and imports no
  YellowhammerKit module. A view that knows a Card, a Feature or a Block Reason belongs in
  `Features/Shared`.
- **Views are dumb.** They take plain values (snapshots) and report intents out — the Pulse through
  `openPulseDestination`. They never open a Journal, never import GRDB, and never run `yh`.
- **No empty folders.** A folder appears with its first file, the same rule the package applies to
  modules.
- **`Integration/` needs a decision first.** A new integration, particularly one that sends data off
  the machine, needs a spec ruling before it gets a folder.
- **`DevSupport/Previews` is Debug-only.** Every file there is wrapped in `#if DEBUG`, and the shipped
  app never depends on it.
