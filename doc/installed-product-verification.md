# Installed-product verification (P16.6)

The notarized release is checked once more after it is installed, on a clean Apple Silicon Mac, the
way an Operator installs it: downloaded, dragged to `/Applications`, set up with the production
Linear identity. `scripts/release/verify_installed.py` runs the five checks the roadmap names and
records the evidence for the release.

Spec: `../yellowhammer-spec/docs/tech/investigations/2026-09-13-feasibility-probes.md` → Build and
packaging; `risks.md` OQ9 (the headless notification post), OQ53 (`launchd` fires the Acts) and
OQ74 (jobs name the resolved path of the installed `yh`).

## The checks

| # | Roadmap item | What `verify_installed.py record` checks |
| --- | --- | --- |
| 1 | `Contents/MacOS/yh` runs under a bare environment | `env -i yh --help` and `env -i yh validate` exit 0; `yh`'s embedded version and build equal the app's. |
| 2 | The headless notification post works from the installed bundle identity | Spotlight knows exactly one `dev.yellowhammer` bundle, the installed one (a second copy, a mounted DMG among them, lets LaunchServices open the wrong app). The engine's own `open -n -g -W -b dev.yellowhammer --stderr … --args --post-notification …` exits 0 with nothing on the app's stderr, and the Operator confirms the notification appeared. |
| 3 | `launchd` jobs generated by `yh setup --install-jobs` fire the installed `yh` | The Project's three LaunchAgents are loaded, and both the plist and the program `launchd` loaded name the installed `yh`. One job is kickstarted; its process is that `yh` and exits 0. |
| 4 | `yh doctor` passes with Orca ADE, at least one CLI and the production Linear identity | `yh doctor --probe --project <id>`, run with the LaunchAgent's `PATH`, exits 0 with Linear authorization and at least one probe passing. `orca` on that `PATH` is at least `check-prerequisites.sh`'s minimum. `config.toml`'s Linear `client_id` is the production app's. `yh doctor` itself has no Orca ADE check, so the tool adds one. |
| 5 | Quitting and never opening the app does not affect a scheduled Act | **5a:** the job fires and exits 0 while the window app never runs. **5b:** the app is opened, the job fired, and the app quit while `yh` still runs; the Act still exits 0. To make that overlap certain instead of a race against how fast the Act finishes, 5b polls `launchctl print` fast (every 0.05s) for the fired job's *running* pid and pauses it with `SIGSTOP` the instant it appears, then quits the app while the Act is stopped and only `SIGCONT`s it afterward (always, in a `finally`) — the Act cannot finish on its own while paused, so the overlap is certain rather than raced. If the app hasn't quit within 10s of being asked to (a paused Act could in rare cases be holding the Journal's write lock, which the app cannot quit while held), 5b resumes the Act and retries rather than waiting indefinitely. It also retries if the Act finished before it could be paused (a real surprise, reported as inconclusive) or if pausing it raced its own exit, and fails outright — not a retry — if the Act is gone once the app has quit: that would mean quitting the app killed it, exactly the defect this check exists to catch. Up to three attempts before failing. |

Each check runs even when an earlier one fails. `record` writes `<n>-*.log` per check and
`verdict.json` (host model and macOS version, the app's and `yh`'s version and build, one result
per check) and exits 0 only when all five pass. `check` reads `verdict.json` back and exits 0 only
for five passes at the expected version.

## Preparing the Mac

- Apple Silicon, macOS 26.0 or later, with no earlier copy of Yellowhammer: `mdfind
  "kMDItemCFBundleIdentifier == 'dev.yellowhammer'"` prints nothing, and neither
  `~/.config/yellowhammer` nor `~/Library/LaunchAgents/dev.yellowhammer.*` exists.
- `scripts/check-prerequisites.sh` passes: `git` 2.38 or later, Orca ADE, at least one agent CLI.
- A clone of this repository at the release tag, used only to run `verify_installed.py`.
- The **production** Linear app's client id and secret (see
  [linear-identity-runbook.md](linear-identity-runbook.md)). The scratch app must never be on this
  Mac.
- A dedicated verification Project: its own Linear project, a throwaway Repo and an empty Spec
  Source, so that the fired Act has nothing to author, build or land. Its Acts run for real against
  the production workspace.

## Running it

1. Download the DMG and `SHA256SUMS` from the GitHub release in a browser, so the files carry the
   quarantine flag, and check the DMG against `SHA256SUMS`.
2. Open the DMG, drag `Yellowhammer.app` to `/Applications`, and eject the DMG.
3. Open the app from `/Applications`. `spctl --assess -v /Applications/Yellowhammer.app` reports
   `source=Notarized Developer ID`.
4. `/Applications/Yellowhammer.app/Contents/MacOS/yh setup --install-jobs`, or the app's Setup:
   production Linear identity, the Operator identity, **allow notifications**, and the verification
   Project.
5. Quit the app, then run:

   ```sh
   python3 scripts/release/verify_installed.py record \
       --app /Applications/Yellowhammer.app --project <id> \
       --production-linear-client-id <production client id> \
       --evidence-directory ~/yh-evidence-<version>
   python3 scripts/release/verify_installed.py check \
       --evidence-directory ~/yh-evidence-<version> --version <version>
   ```

   Allow Terminal to control Yellowhammer when macOS asks: 5b quits the app with AppleScript.
   `--act` picks which Act's job is fired (default `build`).

6. Zip the evidence directory and attach it to the release (`gh release upload <tag> …`).
7. `yh project remove <id>` unloads the verification Project's jobs; archive its Linear project.

Unit tests: `python3 -m unittest discover -s scripts/ci/tests -p 'test_verify_installed.py' -v`.
